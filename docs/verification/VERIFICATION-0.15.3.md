# Перевірка 0.15.3 · Dropbox Business

Причина порожнього списку: новий вхід раніше отримував personal scope за замовчуванням. У Business member/home namespace може бути порожнім, тоді як робочі папки розміщені в бізнес-корені. Автоматичне ввімкнення Cloud Files після вибору локальної папки блокувало ручний перемикач і залишало це підключення у неправильному просторі. Розділення namespace описане в [Dropbox Team Files Guide](https://developers.dropbox.com/en-us/dbx-team-files-guide).

Тепер вибір походить із get_current_account поточного авторизованого входу: Business використовує його бізнес-корінь, особистий вхід — його особистий корінь. Облікові записи не об'єднуються; запити кожного підключення мають тільки його token і namespace. Ручний перемикач прибрано. Business-вхід позначено в боковій панелі. Невідомий root_info не підміняється порожнім personal-списком.

Дерево Dropbox використовує неглибокий list_folder з пагінацією та include_mounted_folders у тому самому namespace, що й нативний транспорт. Воно не завантажує весь проект під час відкриття кореня. Чинний access token не запускає зайвий about; за потреби оновлення збережено rclone refresh. HTTP-читання дерева не створює зовнішній тимчасовий config, який міг би перезаписати щойно оновлений token.

Старе порожнє нативне підключення виправляється зі збереженням абсолютного локального шляху та owner. Перед зміною перевіряються native catalog, durable intents, пари, власні диски, активні передачі, локальні файли та cache. Helper повторно перевіряє власність і порожність кореня перед releaseEmpty. За наявності локальних даних або історії активних пар автоматичний перехід блокується; файли та cloud namespace не перепризначаються. Виправлення не вимагає очищення облікових даних.

Пройдено 68 unit/integration tests, native/provider smoke і source UI з реальним rclone. Окремий source та packaged account-root smoke відтворюють старий Business-вхід із уже зареєстрованим порожнім NTFS-коренем. Реальний Cloud Files root безпечно перепідключається, бізнес-папки з'являються, owner і шлях зберігаються. Особистий тестовий token бачить тільки Personal-only; Business token — тільки business-root. Спроба зміни зайнятого локального кореня відхиляється зі збереженням unsent.txt. Непередбачені cloud mutations у fixture заборонені. Reset завантажує placeholder у звичайний локальний файл, тестові реєстрації прибрані.

На випусковому runtime пройдено також storage smoke: online/cache/pinned, перезапуск, дві мови та компактні стовпці; upgrade smoke із 0.14.5 зі збереженням зашифрованого входу, native owner, правил, журналу, незавершеного видалення та власного subst. Фінальний runtime порівнюється з перевіреним кандидатом, ZIP і publish перевіряються за SHA-256.

Межі: API-відповіді Business/Personal у smoke ізольовані й детерміновані; чужі/реальні Dropbox-файли не використовувалися для запису або тестового видалення. Це перевірка контрактів API та справжньої локальної CfAPI поведінки, а не твердження про проведений наскрізний тест із production-акаунтом користувача. Формат профілю та схема SQLite залишилися сумісними з 0.15.0.
