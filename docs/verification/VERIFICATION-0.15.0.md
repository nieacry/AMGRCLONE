# Перевірка 0.15.0 · Windows

Профіль перенесено до системної папки Документи/AMGRCLONE. Одноразове перенесення зі старого AppData виконується після отримання спільного зі старими випусками singleton-lock, до запуску Chromium і safeStorage. Копіюються лише дозволені файли, перевіряються SHA-256; наявний новий профіль не перезаписується. Старий каталог залишається незмінним. Службові workdir bisync переприв'язуються до скопійованого стану, абсолютні папки проектів не змінюються.

Перед зміною версії створюється приватний знімок профілю: зашифровані входи, SQLite online-backup з WAL, bisync state та native-cache. Формат профілю, мінімальна версія й схема перевіряються до робочих змін. Міграція схеми транзакційна; невдала міграція відкочується. Вбудований rclone береться з нового випуску, явний custom binary зберігається. Автозапуск поновлює шлях поточного зовнішнього EXE; у тестах реєстрація автозапуску ізольована від Windows користувача.

Перевірено реальне оновлення з архівної 0.14.5 до розпакованого ZIP 0.15.0 на окремому Windows-профілі. Збережено зашифрований вхід, мову, налаштування старту, правила, локальний корінь, native owner, driveOwner, плейсхолдери, історію файлів і durable deletion. Незавершене видалення завершується після оновлення. Власний subst-диск зберігає ID, букву й ціль; читання через букву повертає очікувані bytes. Одночасний запуск старої та нової програм заблоковано. Перезапуск нового випуску та безпечний reset тестового профілю успішні.

Картка локальної папки присутня тільки в Усі файли; у Журналі, Дисках і Правилах її немає. Підпис над меню прибрано. У дереві потрібної папки є буква власного диска, стан і підказка з абсолютним шляхом. У налаштуваннях показано розташування профілю, інструкцію оновлення та штатний вихід для заміни папки. UI перевірено автоматичними assertions і переглядом screenshot налаштувань.

Під час перевірки повторного reset після невдалої hydration виявлено 0x80070006 у detach. Довга hydration більше не використовує exclusive oplock: застосовано звичайний attribute handle, як у pin/local. Короткі операції з protected handle тепер утримують CfReferenceProtectedHandle/CfReleaseProtectedHandle згідно з [контрактом Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfgetwin32handlefromprotectedhandle). Власність і dirty-захист залишилися обов'язковими. Додано реальний CfAPI regression: перше завантаження при detach навмисно завершується помилкою, placeholders і реєстрація залишаються, повтор завантажує всі bytes і лишає звичайні локальні файли. Раніше невдало завершений тестовий корінь теж безпечно відключено новою реалізацією.

Пройдено загальні unit/integration tests і шість перевірок профілю, включно з WAL, майбутнім форматом, rollback, workdir і вибором binary. Пройдено source UI з реальним rclone та native/provider smoke. На випусковій Windows-збірці пройдено upgrade, desktop/drive/tray/minimized/restart, onboarding, marker cleanup, reset із cookies та незбереженими файлами, logout/missing-root recovery, journal зі скролом/пошуком/фільтрами/ізоляцією акаунтів, recycle/permanent-delete/orphan/offline retry і launcher з Unicode/пробілами. ZIP перевіряє повноту файлів і має SHA-256; містить лише програму, вихідні файли й інструкції, без профілів користувачів.

Межі: cloud transport у destructive smoke — локальний adapter, а не живий Dropbox. Це не сертифікація всіх production-сценаріїв; великі бібліотеки, сторонні застосунки, тривалий offline та командні конфлікти потребують випробувань у вашому середовищі. Профільний snapshot не є резервною копією всього Dropbox. Встановлення оновлень ручне, через заміну всієї папки; update server, підпис Windows, macOS File Provider та будь-яку інтеграцію з Maya не додано.
