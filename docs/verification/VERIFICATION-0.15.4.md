# Перевірка 0.15.4 · переносимий ZIP і відновлення Cloud Files

Read-only діагностика проблемної папки показала відсутній CfAPI kernel root при наявній Shell-записі. 0x80070186 відповідає ERROR_CLOUD_FILE_NOT_UNDER_SYNC_ROOT у Windows SDK. Відтворено точний збій архівною 0.15.3: зареєструвати порожній тестовий корінь, завершити процес, видалити й пересоздати каталог, спробувати нове підключення з іншим owner. CfRegisterSyncRoot виконувався перед Shell Register; заміна старої Shell-прив'язки прибирала щойно створений kernel root, і наступний CfConnectSyncRoot повертав 0x80070186.

У 0.15.4 перевірка власності передує змінам, дозволені лише власні застарілі Shell-записи поточного SID для того самого порожнього шляху без kernel registration. Чужі активні корені, інші шляхи та непорожні папки не перепризначаються. Shell registration виконується перед остаточним CfRegisterSyncRoot; після цього явно перевіряється owner kernel root і встановлюється connection. Порожній Shell Context після втрати kernel registration обробляється як відсутнє поле; він не підміняє перевірку ID, SID, шляху та kernel ownership. Принципи API: [CfRegisterSyncRoot](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfregistersyncroot), [офіційний CloudMirror](https://github.com/microsoft/Windows-classic-samples/blob/main/Samples/CloudMirror/CloudMirror/CloudProviderRegistrar.cpp).

Невдало підключений порожній корінь без native catalog/intents можна відключити через releaseInactiveEmpty, без успішного init і без мережних запитів. Helper повторно перевіряє порожність і власні реєстрації. Невідомі cached bytes блокують reset та залишаються. Службовий index-scope файл закривається перед видаленням; власна Search-реєстрація прибирається до Shell unregister. У діагностиці тепер є фаза init/register/connect, а 0x80070186 і вже активне підключення мають окремі локалізовані повідомлення.

Випуск містить Electron, rclone і статично зібрані /MT launcher та provider. Перед створенням ZIP перевіряються x64 PE imports і delay imports усіх EXE/DLL. Відсутні сторонні runtimes, включно з VC/Node/Python, відхиляються; дозволені лише bundled modules та відомі компоненти Windows/API Sets. Звіт включено до release/portability.json; українські й англійські інструкції першого запуску — до release/START-HERE.*.md. Профіль не входить до архіву.

Пройдено 68 unit/integration tests і native/provider smoke. Реальний registration smoke використовує стару 0.15.3 для відтворення помилки, а потім перевіряє відновлення новим helper, повторне підключення, reset без init/cloud, захист невідомого кешу, іншого активного owner і непорожньої папки. На packaged runtime пройдено також onboarding/reset із невдалою hydration та незбереженими файлами, logout/missing-root recovery, recycle/permanent delete/orphan/offline retry та Business/Personal isolation.

Реальний distribution ZIP розпаковано в окрему папку. App запускався через зовнішній launcher із PATH тільки Windows/System32, без NODE_PATH/NODE_OPTIONS та ізольованим профілем. Перевірено OS encryption, bundled rclone, реальний NTFS placeholder та hydration. Після штатного виходу вся програма переміщена в інший Unicode/spaced path; повторний запуск зберіг профіль, абсолютний native root та bytes. Тестовий профіль безпечно скинуто. Остаточний runtime порівнюється з перевіреним кандидатом, ZIP і publish — з manifest SHA-256.

Межі: це не запуск на окремій чистій Windows VM. Перевірено статичні залежності та обмежене оточення на поточній Windows. Потрібні підтримувана Windows x64 з Cloud Files і NTFS-папка синхронізації. Destructive cloud-сценарії використовують локальні fixture transports; реальні файли користувача та Dropbox не видалялися. Службові реєстрації порожніх тестових папок прибрані; живу копію користувача в tmp не зупиняли примусово й не переписували.
